TWENTY IS BREAK-GLASS, NOT THE BUDGET.** Operator, 2026-09-05, in two messages — first _"An ABSOLUTE HARD rule for this session: cap the number of total agents for each and every workflow to UNDER 20"_, then, unprompted, _"Ideally, I'm expecting less than 10. 20 is for the 'break glass' scenario, which you should gratuitously consider WHEN to deploy such workflows."_ ⚠ **The second sentence is the real instruction: the question is not how wide the fan-out is, it is whether it should exist.** A 7-attacker fleet was launched here for a 3-file diff whose two leading hypotheses I had ALREADY answered by hand from the repo's own live-measured tests — the breadth was habit, not need. ⚠ **HARD CEILING, 2026-09-05: UNDER 20 TOTAL AGENTS PER WORKFLOW** — operator, verbatim: _"An ABSOLUTE HARD rule for this session: cap the number of total agents for each and every workflow to UNDER 20."_ **"Each and every"** means the budget is per WORKFLOW RUN, attackers plus refuters plus every later stage, not per stage. This supersedes the 69 below, which is now only the history of how the rule was arrived at.

⚠ **A PER-STAGE CAP DOES NOT ENFORCE A TOTAL.** Measured the same day: a 7-dimension fan-out with `CAP = 3` refuters *per dimension* has a worst case of 7 + 21 = **28**, and reads as compliant right up until the findings arrive. When the total is what is capped, the refute stage must take a **single global budget** (`ordered.slice(0, TOTAL_CAP - finders)`), which means it cannot be a `pipeline()` that streams per dimension — it has to collect every finding first. Pay the wall-clock; the cap is the harder constraint.

⚠ **AND I RE-MADE IT ANYWAY, 2026-09-11, WITH THIS ENTRY ALREADY WRITTEN.** The paragraph above describes the bug exactly — a per-dimension cap inside a streaming `pipeline()` — and the #869 round-3 review used 7 dimensions × `slice(0, 4)` findings × 2 skeptics, worst case 7 + 56 = **63**, actual **27**, against an operator cap of 20. Round 4 was 5 × 3 × 2 = worst case 35 and landed on 15: **compliant by luck, not by construction.** Prose in a memory did not stop it, because I checked the SHAPE against the rule and then estimated the NUMBER instead of computing it.

⚠ **SO THE RULE IS NOW A MECHANISM, NOT A HABIT. Before any `Workflow` call, do both, in this order:**
1. **Write the worst case as arithmetic in the script itself**, next to `meta`, and refuse to launch if it exceeds the cap: `const FINDERS = 5, PER = 2, CAP_TOTAL = 12; const MAX_VERIFY = CAP_TOTAL - FINDERS; // 7 verifier slots, global`.
2. **Spend those slots from ONE counter the verify stage decrements**, never a per-item `slice`: collect every finding at a barrier, `const queue = all.slice(0, Math.floor(MAX_VERIFY / PER))`, and `log()` `droppedPastCap` with the locations. A `pipeline()` cannot do this — it has no barrier at which the total is known — so a capped review is a `parallel()` fan-in by construction.
3. **State the worst-case number to the operator in the same message that launches it.** A number I have to say out loud is one I have to compute; "realistically fewer" is the tell that I estimated.

**Superseded ceiling (history): 69 agents per workflow. Target: 15 or fewer.** Operator, 2026-08-30, after a review fleet reached ~94 agents and the operator had to say so twice — first _"Keep your workflows within 69 agents pls, no need to overcomplicate this"_, then _"I'm seeing almost a hundred agents running here… I thought I told you to keep the count under 69?"_ and _"the 'Verify' list of agents is still expanding"_. The session's `workflowSizeGuideline` was afterwards set to **medium — under 15 agents**, which is the number to design for; 69 is the ceiling for a case that genuinely needs it, not a budget to spend.

**Why:** the count is not a private implementation detail — the operator watches the live fleet, and a fan-out that keeps growing on screen reads as a runaway. It is also the *shape* that is wrong: an N-findings × M-refuters stage has no ceiling of its own, so the total is whatever the finders happened to return. Cost was never the objection ("no need to overcomplicate this" is a complexity objection), and ultracode being on does not lift it.

**How to apply:** compute the worst case **before** launching and write it into the script and into what you tell the operator — `finders + (CAP × refuters)`, never "roughly". Any stage whose width comes from a previous stage's output MUST carry an explicit `const CAP = n` and `deduped.slice(0, CAP)`; a `.map()` straight over findings is the bug. Do not edit a running workflow's script to change its cap: the running fleet already loaded it, and the edit only changes the resume cache key. See [[background-workflow-shell-hang]] and [[workflow-dead-agent-reads-as-clean-bill]] for the other two things a fan-out gets wrong.

⚠ **UNDER A SMALL CAP, HAND-TRIAGE IS THE PRIMARY PATH — BUDGET FOR IT, DO NOT TREAT IT AS THE FALLBACK.** Measured 2026-09-05 on #855: 7 attackers returned 7 findings and a global refute budget of 2 judged **2**, leaving **5** for me. Of those 5, three were real and shipped as fixes, two I refuted myself — so the automated refuters judged under a third of the set and the *hand* pass produced every confirmed finding. Two useful consequences: sort the refute queue by severity but never believe the sort (a finder's severity guess precedes verification, and here the two auto-judged ones were both DOWNGRADED while three hand-judged ones were CONFIRMED); and when the budget is small, **read every finding yourself before deciding the round is clean** — the refuters are a sampling aid, not the filter.

⚠ **A BINDING CAP IS AN UNREVIEWED FINDING SET, NOT A TRIM — AND THE DROPPED ONES ARE NOT THE WEAK ONES.** Measured over `#717`'s rounds 4–8: the cap bound four times and dropped **19** findings; every single one I hand-triaged turned out to be real, including two the finders had ranked LOW that were defects in the fix under review. Sorting by severity does not save you, because a finder's severity guess is made before any verification. So: always return `droppedPastCap`, always `log()` the count and the locations so the truncation is visible on screen, and **triage every dropped item by hand before calling the round clean** — a round with `confirmed: 0` and `droppedPastCap: 3` has not reported zero findings, it has reported three you did not look at. Raising the cap is the wrong fix; it is the reading you owe, not the budget.
