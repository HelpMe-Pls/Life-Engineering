In a **background** Workflow (or backgrounded Agent), a subagent's Bash call that triggers a permission prompt **blocks forever** — there is no interactive approver. Seen 2026-06-15 (ENH-2 #87 review): an `Explore`-type review agent (resolved to **Haiku 4.5**) ran `cd …/website && …` (a `cd` compound command trips a permission prompt per the Bash tool docs) and sat **idle 31 min**, stalling the whole workflow at 21/22 agents.

**Why:** background runs have no human to approve Bash prompts; the lower-tier `Explore`/Haiku default also ignores "use `git -C`, not `cd`" instructions more readily than Opus.

**How to apply** — for read-only review/search workflows:
1. **Forbid `cd` and all gate/build commands** (npm/pnpm/eslint/tsc/vitest/next/build) explicitly in the agent prompt; tell agents to use the **Read tool** + at most one `git -C <abs-repo> --no-pager diff`. List the changed files so they can Read directly. Prompts that merely SAY "Read … grep …" without explicitly banning `cd` are NOT enough — an agent will still run a `cd`-compound and wedge (reconfirmed 2026-07-08: a `map:waveboard` mapper hung **idle 47 min** while its 3 siblings finished, because the prompt didn't forbid `cd`).
2. **Omit `agentType: 'Explore'`** so agents inherit the Opus main-loop model (better instruction-following) instead of Haiku.
3. **`TaskStop` a wedged run and re-launch hardened** rather than resume — resume re-spawns the same fragile verifier agents and can re-hang. The hardened re-run finished cleanly in ~12 min. (If the survivors already answered the question — check `journal.jsonl` for their `result` rows — you may not need to re-run at all; the hung agent's output is often redundant.)

**DETECTION (added 2026-07-08 — the cause was known but I still missed a live hang until the user flagged it):** authoring the mitigation is only half the job — a hang can still occur. After launching a background workflow of this shape, **actively watch for the idle state**; don't assume "background = it'll notify me." A hung agent never completes and never fires a notification — it just shows **`idle Nm`** on the `/workflows` panel while siblings finish. Habit: once the FIRST agent of a fan-out returns, glance at `/workflows` (or read `journal.jsonl` — `started` rows with no matching `result` = still-running; if wall-clock ≫ the median sibling's time, suspect a hang). Treat **idle > ~10 min with siblings done** as hung → TaskStop. Do NOT let it ride to the 45-min cap.

**⚠ 2026-07-27 — A HARDER FAILURE THAN THE HANG: backgrounded `Agent`-tool subagents produced ZERO reports, twice, and were UNDETECTABLE by the documented method.** During the PR #357 review I spawned 5 review agents, then respawned 4 more after a session resume. **All 9 returned nothing.** Never a completion notification, never a reply to a `SendMessage` status ping (3 rounds of pings, including "STOP and send whatever you have"). The second batch was hardened exactly as this memory prescribes — prompt said "**Do NOT use the Bash tool at all, not once**", Read/Grep/Glob only, file lists pre-supplied, no `agentType` override — and still produced nothing, so **this is not the `cd` permission hang.**

Detection notes that matter:
- **`TaskList` returns "No tasks found"** for `Agent`-tool subagents, so there is no id to `TaskStop` and no idle timer to read. The `journal.jsonl` / `/workflows` technique above applies to the **`Workflow`** tool, NOT to backgrounded `Agent` calls — do not assume it covers both.
- A **session resume silently orphans in-flight agents**: batch 1 belonged to the pre-resume session and could never have replied. If the session id changes (visible in the scratchpad/task output paths), treat every outstanding agent as dead.

**How to apply:** for anything on the critical path, do NOT depend on a backgrounded `Agent` fan-out. Either pass `run_in_background: false` so the result is in hand before continuing, or do the review directly and treat agents as pure upside. Give yourself an explicit checkpoint (~10 min or "when the first sibling returns") and if nothing has landed, **proceed on your own work rather than re-pinging** — pings went 0-for-3 here. In this session the direct review found and fixed 6 real issues while the fan-out contributed nothing, so the fallback is not a downgrade.

**✅ 2026-07-28 — THE `Workflow` TOOL IS NOT AFFECTED, and the distinction is now measured rather than assumed.** Two background `Workflow` runs in one session, on the PR #404 review: **53 agents / 0 errors / 13.6 min**, then **19 agents / 1 error / 11.3 min**. Both returned full structured results, both were readable live in `journal.jsonl`, and both produced findings that changed the work (a real service-role path-traversal escape, and later an AA failure in the first round's own fix). So the 9-for-9 silence above is specific to **backgrounded `Agent`-tool** calls; do not generalise it to `Workflow`.

What made those runs reliable, and is worth repeating verbatim:
- **Hard tool rules at the top of every agent prompt** — no `cd`, no npm/npx/tsc/eslint/vitest/next/playwright/supabase/docker, no writes, Read/Grep/Glob only, and at most ONE named `git -C <abs-repo> --no-pager diff` form. Zero hangs across 72 agents.
- **No `agentType` override**, so agents inherit the Opus main-loop model.
- **A `schema` on every `agent()` call**, so results arrive validated instead of as prose to parse.
- **A refutation panel told to default to `refuted: true` when unsure.** It is harsh — 15 raw findings → 2 survived — so **read the rejections yourself**: three of them leaned on *"pre-existing"* or *"the producer wouldn't do that"*, which is not the same as *"not a defect"*, and one lens **crashed** (`API Error: Connection closed`) so its finding never reached refutation at all. The single most valuable finding of the whole session came out of a crashed lens. Treat the panel as a filter to argue with, never a verdict.
- **One error in 72 agents was a transient API disconnect**, reported in the tool result's `<failures>` block — check that block, because the pipeline drops that stage's findings to `null` silently.

**✅ 2026-08-17, CORRECTED SAME DAY — THEY ARE NOT DEAD, THEY GO IDLE AND WILL ANSWER A DIRECT `SendMessage`.** The two agents below (recorded as silent) surfaced ~25 min later as `idle_notification … "idleReason":"available"`, and a single `SendMessage` each got **both full reports back**, each opening with *"analysis was complete"* — they had finished long before and simply never delivered. Their findings were real and changed the work: one traced a privacy leak I had missed (naming gated on the author's role-NOW, so a DEMOTED admin's address would print into a chapter's log), the other correctly called one of my new tests unfalsifiable. **So the failure is DELIVERY, not the agent.** Revised how to apply: never block on them, do the work yourself in parallel — but **do not write them off either.** Watch for the idle notification, then ping with `SendMessage` naming the agent, and tell it what changed since it started (mine had reviewed an uncommitted diff that was by then a merged commit). Also worth knowing: `TaskOutput` and `TaskStop` do not find them by the id the spawn returned, while `SendMessage` reaches them by NAME — so **always pass `name:` when spawning**, or you lose the only working channel.

**⭐ 2026-08-24 — THE RELIABLE RECOVERY CHANNEL IS THE FILESYSTEM, and it turned a 0-for-4 fan-out into four full reports.** Four named `general-purpose` review agents (adversarial review of PR #641) all went `idle` in `ListAgents` and delivered nothing: no completion notification, and a `SendMessage` to three of them asking for their report produced **no reply at all** — so the 2026-08-17 "ping them when idle" move failed this time. But every agent's transcript was sitting on disk the whole time:

```
C:/Users/leekh/.claude/projects/<project-slug>/<session-id>/subagents/agent-a<name>-<hash>.jsonl
```

One `node -e` over that directory — parse each line, keep the LAST `type:"assistant"` message's concatenated `text` blocks — printed all four complete reports. They were excellent: they found a hole I had independently found (confirming my MED rating should be HIGH), a defect **in the fix I was mid-way through writing**, a third door I had missed entirely (`/login` redirects an already-signed-in visitor and had neither of the two checks I had just added), and two of my own new assertions that could not fail.

**How to apply:** after a fan-out, do NOT conclude the agents produced nothing just because nothing was delivered and pings went unanswered. `ListAgents` showing `idle` means **finished**, and finished work is on disk. Go read it — it costs one command. Recovery beats re-running: those four agents had ~30 minutes of analysis in them. Keep `name:` on every spawn (it makes the filename readable), and note the session id is the same one in your scratchpad path.

⚠ Still true, and this session re-confirmed it: **do the critical dimension yourself, in parallel.** I reviewed the security-critical dimension by hand while the four ran, which is what let their reports arrive as pure upside rather than as a blocker.

**⚠ 2026-08-25 — I HAD THIS WRITTEN DOWN AND STILL DID NOT DO IT.** Five named agents (round 4 of the #630 review) went `idle`, a `SendMessage` to each got no reply, and I told the user "subagents came back empty" and reviewed everything myself. The transcripts had been on disk the entire time. Reading them took one command and produced **six findings, four of which survived my own verification** — including a MEDIUM defect in the fix I had shipped three commits earlier (removing a query filter reversed an accepted cost recorded in the decision log) and a whole-list security pin sitting behind a live-env `ctx.skip()`. **So make it mechanical, not a judgement call:** the moment `ListAgents` shows a spawned agent `idle`, run the recovery script. Do not ping, do not conclude, do not report "they produced nothing" — `idle` MEANS finished, and finished work is on disk. Equally: **verify each recovered finding yourself.** Two of the six dissolved under "which seam owns this rule?" — a loop that re-applies the source's own predicate still catches every mutation in the module under test, and only misses ones belonging to a neighbour that pins them with literals.
