In `website/vitest.config.ts`: `const env = {...loadEnv('','..',''), ...loadEnv('','.','')}` then `test.env: { NEXT_PUBLIC_SUPABASE_URL: env.X ?? '' }` (and ANON/SERVICE). Vite's `loadEnv(mode, dir, '')` with an **empty prefix** iterates `process.env` and includes EVERY key, overriding .env-file values (Vite source `dep-*.js` ~L34927). So when CI exports the LOCAL Supabase keys via `>> $GITHUB_ENV` BEFORE `npm test`, `loadEnv` captures them → `env.X` = local URL (not undefined) → `test.env.X` = local URL → the live RLS/notification suites read `process.env.X`, get the local URL, `ENV_OK=true`, and **RUN** (no longer skip). Vitest applies `test.env` with UNCONDITIONAL assignment (`process.env[k]=env[k]`, setup-common chunk), but that's harmless here because loadEnv already fed the real value in.

**Empirically proven 2026-06-22** with the exact repo pattern (a `PROBE_KEY=hello` flowed through to the worker). A code-review agent once "confirmed" the suites SKIP in CI — that is WRONG; do NOT add a `?? process.env.X` fallback to vitest.config thinking it's needed.

**UPDATE 2026-06-24 — that prod-safety gap is CLOSED (the earlier "no local-only guard" claim is now STALE).** `website/vitest.config.ts:22-40` has a config-level guard: it computes `supabaseIsLocal = isLocalSupabaseHost(rawSupabaseUrl)` (shared with `e2e/fixtures/env.ts`), and for a **non-local** URL it **blanks the Supabase keys** in `test.env` (so the live suites SKIP locally) and **throws** when `process.env.CI` is set. So a LOCAL `npm test` with `website/.env` pointing at prod does NOT mutate prod — the live suites skip (verified this session: offline `npm test` → 411 passed / 11 skipped; live run with exported `127.0.0.1` keys → 422/0). The individual suite files (e.g. `intake-rls.test.ts`) still gate only on `ENV_OK = URL && ANON && SERVICE`, but the config blanks those keys for a remote URL, so the net behavior is local-only. See [[e2e-cicd-local-supabase-prod-safety]].

**UPDATE 2026-09-10 — THE OPERATIONAL HALF, AND IT BIT ME.** Local Supabase RUNNING is not enough: a hand-run `npm test` still SKIPS every live suite and still exits **0**. Two reasons, both easy to miss. (1) `package.json` "test" is bare `vitest run` — **`scripts/assert-full-suite.mjs` is NOT in it**; the judge that refuses a skipped run exists ONLY inside `.githooks/pre-push`. (2) The hook is also what supplies the keys: it runs `npx supabase status -o env`, re-exports them as `NEXT_PUBLIC_SUPABASE_URL` / `_ANON_KEY` / `SUPABASE_SERVICE_ROLE_KEY`, and refuses to gate at all if Supabase is down. `website/.env` points at PROD, so without that export the config-level guard blanks the keys and the suites opt out. Measured: bare `npm test` → **297 files / 2927 passed / 81 skipped, exit 0**; the same tree with the hook env → **298 / 3008 / 0 skipped**, judge exit 0. **To show a real full-suite green by hand, reproduce the hook env first** (`eval` the `supabase status -o env` block, export the three names, then `npm test`, then `node scripts/assert-full-suite.mjs <log>`) — and read the exit code of `npm test`, never of what it was piped into (the hook does this with `PIPESTATUS`, deliberately). A push gates correctly regardless; it is the manual verification run that lies. See [[e2e-cicd-local-supabase-prod-safety]].
